# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FluRai is an Android app (Kotlin + Jetpack Compose) for learning Japanese: SRS vocabulary cards, grammar, tests, reading, video and media recommendations, streaks, and later an AI conversation partner, measured against JLPT N5–N1. The feature roadmap is built one milestone at a time (milestone numbers appear in `PlannedFeature` cards on each tab).

**Start every session by reading [docs/ROADMAP.md](docs/ROADMAP.md).** It holds the full plan, the research behind it, and a status table showing which milestone is merged, in review, or next. Update that table when you open or merge a milestone's PR.

## Commands

Use Android Studio's bundled JDK (the `java` on PATH is an old JDK 13):

```bash
export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"
./gradlew assembleDebug          # APK -> ~/.flurai-build/app/outputs/apk/debug/app-debug.apk
./gradlew testDebugUnitTest      # all unit tests
./gradlew testDebugUnitTest --tests "com.flurai.app.core.model.JlptLevelTest"   # one test class
./gradlew lintDebug
```

Content pipeline (Python 3.12+, stdlib only; downloads are cached in `tools/content/.cache`):

```bash
python -X utf8 tools/content/build_content.py           # rebuilds app/src/main/assets/content.db
python -X utf8 -m unittest discover tools/content       # pipeline tests, incl. checks on the built db
```

There is no emulator. The user tests on their phone: build `assembleRelease` (R8-optimised, signed with the same key, so it updates over any earlier build) and send `~/.flurai-build/app/outputs/apk/release/app-release.apk`. Debug builds are several times slower in Compose, so don't judge speed from them. After changing code that R8 could strip (reflection, serialization, Firestore mapping), check `app/proguard-rules.pro`.

**Signing:** both debug and release builds are signed with the FluRai release key in `~/.flurai-signing/` (`flurai-release.jks` + `keystore.properties`, outside the repo and OneDrive). Test APKs and releases therefore update each other in place. Never commit the key. If it is missing, builds fall back to the standard debug key, and those APKs can't update an installed release.

## Firebase

Project `flurai-app` (console: https://console.firebase.google.com/project/flurai-app), Android app `com.flurai.app`. `app/google-services.json` is gitignored; recreate it with:

```bash
firebase apps:sdkconfig ANDROID 1:451607396485:android:bf1319f7372c68d38829ec --project flurai-app --out app/google-services.json
```

The Email/Password sign-in provider must be enabled in the console (Authentication → Sign-in method); without it sign-up fails with `ERROR_OPERATION_NOT_ALLOWED`.

## Build quirks

- The project path contains Hebrew characters. `build.gradle.kts` moves every module's build dir to `~/.flurai-build/<module>` (the unit-test JVM breaks on non-ASCII classpaths on Windows), and `gradle.properties` sets `android.overridePathCheck=true`. Look for outputs and reports there, not in `app/build`.
- AGP 9 has built-in Kotlin: don't apply `org.jetbrains.kotlin.android`. Hilt uses KSP.
- `local.properties` must escape the drive colon (`sdk.dir=C\:/Users/...`) or lint fails.

## Architecture

- Single `app` module, package `com.flurai.app`. Packages are split by feature (`ui/home`, `ui/learn`, `ui/explore`, `ui/profile`, ...) and shared code (`core/model`, `ui/components`, `ui/theme`).
- `MainActivity` → `FluRaiTheme` → `FluRaiAppShell`: a `Scaffold` with a bottom `NavigationBar` and a type-safe Navigation Compose `NavHost` (routes are `@Serializable` objects). Tabs: Home, Learn, Explore, Me.
- DI: Hilt (`@HiltAndroidApp FluRaiApp`, `@AndroidEntryPoint MainActivity`); bindings in `core/di/AppModule.kt`.
- `FluRaiRoot` switches on `AppViewModel.state` (`AppState`: Loading → SignedOut → NeedsOnboarding → Ready). It shows `AuthFlow` (welcome/sign-up/sign-in/reset), `OnboardingScreen`, or the tab shell, which receives the `AuthUser` and `StudyProfile`.
- Auth: `AuthRepository` (Firebase email/password; the display name is the user's name). Firebase error codes become user-facing text in `AuthErrors.kt`; ViewModels only ever see `AuthException` messages.
- **Study content** (`core/content`): a read-only Room database (`ContentDatabase`) copied from `assets/content.db`. That file is built by `tools/content/build_content.py` from JLPT lists, JMdict/KANJIDIC2 and Tatoeba, using Room's exported schema in `app/schemas/` so it always matches the entities. **To change a content table:** edit the entity, bump `ContentDatabase.version`, run `./gradlew kspDebugKotlin` (exports the new schema), then re-run the pipeline. Word ids come from `tools/content/word_ids.tsv` (Anki guid → id) and must never be renumbered, because user progress will refer to them; commit that file after a rebuild. `jlpt` columns hold the JLPT number (5 = N5, easiest).
- **Flashcards** (`core/srs`, `core/study`, `ui/study`):
  - `FsrsScheduler` is a port of py-fsrs 6.x (FSRS-6, Anki's scheduler); `FsrsTest` pins it to values generated by py-fsrs, so regenerate those if you touch the math.
  - Progress lives in a separate Room `UserDatabase` (`user.db`: `card`, `review_log`, keyed by Firebase uid). Unlike the content DB it is never recreated, so **schema changes need a Room migration**.
  - A card is (item type Word/Kana, item id, kind Recognition/Production). New words get a recognition card; the production card unlocks when recognition first graduates to Review.
  - `StudySession` (core/study) is one flashcard session: it owns the queue, reveal/answer, bury/suspend, learn-more and the finished-screen rules, and exposes everything on screen as `state`. It takes `CardContentSource` (the database in the app via `DatabaseCardContent`, a map in tests), a `StudyClock` and a `now` function, and has no Android in it; `ReviewViewModel` only adds the route, the profile, the clock's lifecycle and speech (a Listening card's audio plays when it appears). `StudySessionTest` plays sessions against the shared fakes in `StudyFakes.kt`. Change session behavior there, not in the ViewModel.
  - The daily new-word count (`StudyDao.introducedSince`) comes from the review log: a first answer in a session is logged with `state_before = 0`. A word added by hand (`addToStudy`) already has a card, so it never uses the allowance, and its card keeps its real creation time (sync relies on that).
  - `StudyQueue` orders a session (due learning → reviews → new → learn-ahead 20 min). `StudyRepository.loadSession` picks new items (`StudySource`: Auto follows the profile; beginners get kana first; words in Genki-lesson order). Study days roll over at 4 a.m. (`StudyDay`).
  - Audio comes from Android TextToSpeech (`JapaneseSpeaker`); speak the kana reading, and only after the answer is revealed. The exception is the Listening card (`CardKind.Listening`, unlocked together with Production when recognition graduates, gated by `AppSettings.listeningCards`; `dueCards`/`dueCount` take a `listening` flag so turning it off hides existing ones): its audio plays as the card appears. The Listening quiz (`QuizKind.Listening`, `QuestionKind.WordListening`, `TestType.Listening`) works the same way; `JapaneseSpeaker.speak` remembers a request made while the engine is still starting.
- **Custom decks** (`core/study/Decks.kt`, `ui/study/Deck*`): `deck` + `deck_word` tables (UserDatabase v6, `MIGRATION_5_6`) hold the learner's own word lists; cards are never copied, a deck only lists word ids. Any chosen `StudySource` (Deck, Level, KanaDeck; not Auto) makes `loadSession` offer only that deck's due cards and new words, ignores the daily new-card allowance, and the finished screen continues with that deck only (`DeckWords` is the small interface `StudyRepository` uses). Built-in decks open `SourceDeckScreen` (`SourceDeckRoute`) before studying. Added from the word page (`DeckPickerDialog`) and Media (`saveAsDeck`). Synced like channels as one `meta/decks` document (restored only onto a phone with no decks), moved/wiped by `AccountDao` like the other tables.
- **Progress** (`core/knowledge`, `ui/progress`): `CardEntity.knowledge()` classifies a word by its recognition card (FSRS stability ≥ 7 days known, ≥ 21 mature; thresholds in `KnowledgeRules`). `computeProgress` turns all of a user's cards into per-level vocabulary coverage, kanji coverage (a kanji counts when it appears in a known word), weak words (anything forgotten before, worst first) and a 7-day forecast. `estimateLevel` starts from the level chosen at onboarding and moves up while the next level's words are ≥ 80% known; tests (milestone 6) will refine it. All pure functions, covered by `ProgressCalculatorTest`. `ProgressViewModel` feeds both the Home summary and the Progress screen.
- **Study time, streaks, reminders** (`core/activity`, `core/reminder`, `ui/settings`):
  - `study_day` (UserDatabase v2, `MIGRATION_1_2`) holds seconds and reviews per uid and study day. `ActivityTimer` credits time between taps (gap capped at 2 min, stopped while the app is in the background); `ReviewViewModel` drives it from the lifecycle. `StudyActivityRepository.record` writes in an app-level scope so leaving a screen cannot lose time.
  - `computeStreaks`/`summarize` are pure (tested): a day counts at `streakMinutes` (setting, default 5); today unmet does not break the streak until the day ends. The Home `StreakCard` shows it.
  - `AppSettings` (reminder on/off/time, streak minutes) live in DataStore keyed by uid (`SettingsRepository`). `ReminderScheduler` enqueues a 24 h periodic WorkManager job (`ReminderWorker`, dependencies through a Hilt entry point); it skips the notification when today's goal is met. Every study screen credits time through a `StudyClock` (start/tap/pause/resume/finish over `ActivityTimer` + `StudyActivityRepository.record`): flashcards, quizzes, Reading and the grammar point page. Every study screen calls `StudyClockEffects` (ui/components/StudyTime.kt: stops the clock in the background, under another screen and on close); reading-style pages use `rememberStudyScroll(clock)`, which calls it and counts scrolling as activity. New study screens must do the same.
- **Tests** (`core/quiz`, `ui/tests`): `QuizRun` (core/quiz) is one test taken by one learner (questions, answering, adaptive placement stages, scoring, saving, add-missed-words, adopt-placement-level) over a `QuizBackend` (the repositories via `RepositoryQuizBackend`, a fake in `QuizRunTest`); `QuizKind` owns everything that differs per kind (route text, title, saved `TestType`, saved level, pass rule), so a new kind is one case there plus its questions in `RepositoryQuizBackend`. `QuizViewModel` only connects the route, profile, clock lifecycle and the audio of listening questions. `Questions.kt` builds multiple-choice questions (word meaning, kanji reading) with same-family distractors, and holds `PlacementTest`, the adaptive state machine (5 questions per level from N4; 4 right moves up). `QuizRepository` builds placement stages, 20-question checkpoints and quick quizzes, and saves `test_result` rows (UserDatabase v3, `MIGRATION_2_3`). `testedLevel(results)` (a placement result or a checkpoint passed at 80%) lifts the start of `estimateLevel` in `ProgressRepository.snapshot`. `QuizViewModel` runs all three kinds, credits study time like the flashcards, and can add missed words to the flashcards. Grammar and reading questions plug in as new `QuestionKind`s.
- **Grammar** (`core/grammar`, `ui/grammar`): `tools/content/grammar.json` (hand-written: N5 89 points, N4 108, N3 158, N2 95, N1 71; N1 is the thinnest level) is built into `grammar_point`/`grammar_example` (ContentDatabase v2). Each example stores an `answer` that appears exactly once in the sentence; `grammarQuestion` blanks it and takes distractors from other points' answers. `grammar_progress` (UserDatabase v4, `MIGRATION_3_4`) counts right/wrong per point; `grammarStatus`: Known after 3 right with the latest right. Practice runs through the quiz screen as `QuizKind.Grammar`. The list screen shows one level at a time through N5-N1 filter chips (`GrammarListViewModel.selected`, starting at the learner's level). Ids only need to be unique (level comes from the `jlpt` field; ordering inside a level is by id), and never change. To add points, append to grammar.json with new ids, re-run the pipeline, **and bump `ContentDatabase.version`** (installed apps only re-copy `content.db` from the assets when that number goes up; export the schema with `./gradlew kspDebugKotlin` before rebuilding the db).
- **Reading** (`core/reading`, `ui/reading`): sets of six verified Tatoeba sentences per level. `Lexicon` tokenizes by longest match against the word table (no deconjugation; lone kana are not tappable); `sentenceLevel` = hardest matched word, and a sentence with an unmatched kanji word is rejected, so it never lands in an easy level. Pools are computed once per run. 'Check yourself' is `QuizKind.Reading` (`QuestionKind.SentenceMeaning`, wrong options are other sentences' translations). External readers (NHK Easy, Tadoku, Watanoc) are links only. Furigana: `rubyParts(surface, reading)` (core/reading/Furigana.kt, tested) puts the word's reading over each kanji run and none over okurigana; Reading draws sentences as a `FlowRow` of two-line cells (`RubySentence`) because Compose `Text` has no ruby. The on/off choice is `AppSettings.showFurigana`.
- **Videos** (`core/video`, `ui/explore`): a bundled list of YouTube channels per JLPT level (`videoChannels`). Everything links to YouTube *search* URLs, never video or channel ids, so nothing goes stale and no API key is needed. Weak grammar = points with more wrong than right answers. An embedded player and watched tracking would need video ids (not done).
- **Media** (`core/media`, `ui/explore/Media*`): the public jiten.moe API (no key), called from the device with `HttpURLConnection`; jiten.moe forbids mirroring, so results are only cached in memory for 15 min (`MediaRepository`). `difficultyRange(level)` maps a JLPT level to jiten's 0-5 raw difficulty; `coverage` matches a deck's 200 most common words (JMdict ids) against our words via `word.jmdict_id` and the learner's known cards; `wordsToLearn` feeds 'Learn the top words first'. Covers use Coil. This is the first screen that needs the network.
- **Cloud sync** (`core/sync`): `SyncEngine` pulls then pushes (`sync`, never throws; failures land in `status`). It talks to two interfaces, so the whole pull-merge-push runs in JVM tests: `SyncCloud` (document-level: `changedSince`, `document`, `write`, `deleteAll`, `refreshSignIn`; `FirestoreCloud` in the app stamps `updatedAt` with the server's time, reads from the server, and turns Firestore errors into `CloudException`) and `SyncLocal` (plain lookups and writes; `RoomSyncLocal`). The rules live in `SyncCodec.kt` (pure): the document layout (a stored format, field names never change), `needsUpload`, `cloudCovers` (which copy wins), `mergeDay`. `SyncEngineTest` plays one- and two-phone stories against `InMemoryCloud`/`InMemoryLocal`/`InMemoryPrefs` (test sources); add a story there for any sync change. Channels, decks and settings are whole documents (`meta/*`): each part keeps a fingerprint of what this phone last uploaded or took (`UserPreferences.uploadedHash(uid, part)`); the cloud's version replaces this phone's only while the local one still matches that fingerprint (or the phone never synced it and has none), otherwise this phone's wins and is uploaded, so deletes travel both ways and are never undone by a stale cloud copy. Cursors and settings keys are `<uid>.sync.*` in DataStore; `markAllDirty` resets the push cursor (needed after the cloud copy was deleted or progress moved). **A new per-user table** goes in: `UserDatabase` (+ migration), `UserTables` (core/account: its name, what the learner calls it, and its cloud collection), `AccountDao` (a DELETE query called from `wipe()`, an UPDATE ... SET uid query called from `move()`), and, if it is backed up, `SyncLocal`/`RoomSyncLocal`, the codec and `SyncEngine` pull/push (cloud collection names live in `SyncCodec.kt`). `UserTablesTest` fails with a message saying what is missing; the delete-account and erase-guest texts are built from `UserTables`.
- **Guest mode** (`core/auth`): `AuthUser.isGuest` with the fixed uid `GUEST_UID` ("guest"). The flag lives in SharedPreferences (`FirebaseAuthRepository`), so everything keyed by uid (cards, settings, profile) just works. Guests skip email verification and never sync (`SyncEngine.sync` returns false for `GUEST_UID`, and `MainActivity.onStop`/Settings skip it). Leaving guest mode (`signOut`) keeps the data; `MoveProgressCard` then offers to move it into the new account via `AccountMover`, and `EraseGuestSection` wipes it. New code that needs the user id must not assume a Firebase user exists.
- `StudyProfile` (level, daily goal, kana knowledge) lives in DataStore keyed by Firebase uid (`StudyProfileRepository`); no profile = onboarding not done. **Per-user preferences** (`core/prefs`): all accounts' settings share one DataStore as `<uid>.<name>`. `UserKeys` builds those keys (the two repositories use it for single settings); `UserPreferences` does the whole-account operations (export/import for the cloud copy, move, wipe, `levelsByUid`, sync cursors and the uploaded hash). Nothing else builds or splits such a key; sync, `AccountMover` and delete-account go through `UserPreferences`.
- `JlptLevel` orders levels easiest-first (Beginner, N5 … N1). Compare by ordinal, never by the number in the name.
- **Japanese text must use `TextStyle.japanese()`** (`ui/theme/Type.kt`). It sets the `ja-JP` locale so devices with a non-Japanese system language draw Japanese, not Chinese, kanji shapes.
- Theme colors: indigo primary, vermilion secondary, matcha tertiary, washi-paper surfaces. Dynamic color is deliberately off.
- The launcher icon (`res/drawable/ic_launcher_foreground.xml`) is the glyph 流 generated from Noto Sans JP Bold (OFL) with fontTools. Regenerate rather than hand-edit.

## Workflow

- Private repo `yorairh/flurai`. One branch per feature (`feature/NN-name`), push and open a PR with `gh` when it's done; merge only after the user has tested the APK and approved.
- **Versions:** up to 0.23.0 milestone N shipped as `0.(N+1).0`. 1.0.0 is the first release for friends; from then on a fix is `1.0.x`, a milestone `1.N.0`, and `versionCode` goes up by one every release. Bump `versionCode`/`versionName` in `app/build.gradle.kts` in the milestone's PR (the version is shown in the app under Me → Settings → About, so the user can check which build they have; keep it visible), and write its release notes in `docs/releases/<version>.md` (see the earlier ones for the format).
- **After merging a milestone PR:** check out an up-to-date `main` and run `tools/release.sh <version> "<milestone title>"`. It builds the signed release APK, verifies the signature, and creates GitHub release `v<version>` with the notes. Then update the roadmap's status table.
